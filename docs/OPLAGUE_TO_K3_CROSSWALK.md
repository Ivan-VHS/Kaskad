# Соответствие OPlague ↔ математика Kaskad/K3
## Реестр переноса смысловых структур, данных и доказательных границ

**Версия:** 1.0.0  
**Источник:** Ivan-VHS/OPlague, main commit `ab83f8bfbcb3a1b820067a502e6bb1b7f0b4b7e6`  
**Каноническая основа:** Теория Вьюненко K3, основание \(B=1000\), разделитель \(k\).

Этот документ отвечает на вопрос: какую математическую структуру представляет каждый существенный домен OPlague, какие элементы связаны с K3, а какие должны оставаться отдельными типами.

## 1. Правило интеграции

Переносится смысл, ограничения, инварианты и зависимость от источников. Не переносится автоматически:
- программный код;
- неисполняемые проектные пожелания как факты реализации;
- статические оценки как измерения времени выполнения;
- подпись/хэш как доказательство совместимости;
- совпадение ID как доказательство безопасной установки;
- ординальная лексическая шкала как физическая метрика.

K3 используется для точных целых, индексов и позиционных счётчиков. Структуры данных не сводятся к одному числу.

## 2. Карта математических соответствий

| Домен / источник OPlague | Математическая форма | Содержательный инвариант | Роль K3 |
|---|---|---|---|
| PnP inventory, `tools/federation.py` | частичная функция Host → конечное множество DeviceRecord | только фиксированный read-only запрос на поддерживаемой ОС; offline-записи отделены | счётчики, индексы, точные размеры |
| Hardware IDs, `tools/device_graph.py` | канонический язык ID + частичный нормализатор + отношение эквивалентности | \(N(N(x))=N(x)\); только точное равенство | индексы и счёт количества ID; сам ID остаётся строкой |
| Compatibility graph | двудольный граф \(D\sqcup P\) | ребро только при непустом точном пересечении ID | нумерация узлов/уровней, число рёбер; граф не кодируется числом |
| Architecture profiles | конечное множество архитектур + трёхзначный классификатор | match / nonmatch / unknown | целочисленные enum-идентификаторы возможны при таблице версий; семантика enum отдельно |
| INF / ZIP / PE inspectors | частичные парсеры с бюджетами ресурсов | отказ при нарушении пути, формата или лимита | размеры, индексы и счётчики |
| UDRV v1 | манифест-функция Path → (Size, Digest) и контейнерное отображение | точное равенство путей, размеров и SHA-256 | числовые лимиты и количества; путь и digest остаются отдельными типами |
| Authenticode | запись результата проверки подписи с источником и контекстом | подпись не равна совместимости/безопасности | номер/код статуса только как типизированный идентификатор |
| DRIVE-LENS | конечный реестр свидетельств с provenance и HMAC-псевдонимами | exact subject/attribute/window; конфликты сохраняются | счётчики записей; псевдонимы и хэши не переводить в числовую семантику |
| Canonical reports | упорядоченные конечные структуры + каноническая сериализация + SHA-256 | одинаковая каноническая структура → одинаковый digest | длины/счётчики; порядок и байты остаются структурой |
| Metric lab | \([0,1]^n\), евклидова/взвешенная метрика, косинус, ковариация | единицы, направление, одинаковый набор измерений и неопределённость | только после явного квантования с \(\Delta\) и ошибкой |
| GPU telemetry | частичная временная последовательность typed sensor values | null остаётся unknown; источник и время сохраняются | номера датчиков/образцов и точные счётчики |
| Evidence transactions | система состояний staged/committed, generation-CAS, rollback | commit только при совпадении поколения; migration повышает schema version | generation/version — точные целые |
| Local-first store | append-only множество операций + LWW-register | порядок \((Lamport, actor, counter, id)\) детерминирован | счётчик actor, Lamport clock, revision ID |
| Plugin catalog | типизированный конечный реестр адаптеров и capability-меток | metadata discovery ≠ code execution; capability ≠ OS permission | индексы и количество плагинов |
| Workflow planner | конечный DAG + топологический порядок + критический путь | граф ацикличен; dry-run не исполняет шаги | индексы, длительности и число задач |
| OCTA federation | ориентированный граф проектов + 8 фасетных ограничений | 4 узла → 12 направленных peer-связей без петель; 4 self-loop | счётчики графа; топология остаётся графом |
| Atomic-Quantum 133 | конечный каталог из 133 симуляционных операций в 6 семействах | классическая симуляция ≠ наблюдение квантового оборудования | порядковые номера функций и размер семейств |
| CSR-120 | множество нормативных принципов + отдельное множество из 36 проверок | принцип ≠ исполняемый detector | идентификаторы/счётчики; смысл доменов отдельно |
| Impact profiles | 20 векторов в \(\{1,\ldots,5\}^5\), ординальные ранги | лексическая шкала ≠ измерение или рейтинг устройства | целочисленные компоненты можно хранить как группы, сохраняя ordinal type |
| Gaming lab | экспериментальные выборки frame-time + контекст конфигурации | несопоставимые условия не образуют корректное сравнение; регрессия ≠ причинность | счётчики кадров/прогона; измерения остаются вещественными |
| Guarded power-plan restore | конечный автомат с условным переходом | возврат только если текущий профиль всё ещё равен профилю, выставленному сессией | версии/ID перехода; системное действие остаётся отдельным |
| Budget planner | вектор неотрицательных распределений и баланс | \(R=L-\sum x_i\), превышение \(\max(0,-R)\) | точные целые денежные единицы; валюта и единица обязательны |
| Atomic UI settings | versioned document + атомарная замена файла | старый или новый документ; best-effort только для настроек UI | номер версии/поля, но не переносить транзакционные гарантии на ОС |
| CLife governance | конечный автомат жизненного цикла изменений | baseline, checkpoint, isolated patch, validation, human review, recovery | номера checkpoint/версий/состояний |
| Hardware ID linter | частичный синтаксический парсер известных bus ID | неизвестные поля сохраняются, производитель не угадывается | строковые поля остаются строками |
| Authenticode | платформенное свидетельство подписи с контекстом | Windows-only, не сертификат безопасности или совместимости | код/версия результата — enum с отдельной семантикой |
| SPDX / SBOM | конечный inventory-функционал файлов с path+digest+license-state | NOASSERTION сохраняется, хэш не доказывает право на распространение | числовой индекс/размер; license-state отдельно |
| Program Catalog 1000 | конечное множество категорий/идентификаторов | диапазон OPlague 501–700 обозначает зону ответственности, не реализацию всех пунктов | K3 для номеров/диапазонов и счётчиков |
| Universal Division Engine | отношение разбиения, quotient/remainder, DAG зависимостей, allocator | проектный контракт; native engine не реализован | K3 для точных q/r/индексов, с единицами и порядком |
| NEXUS profile | версионированная сеть поставщик→потребитель доказательств | валидность, freshness и unknown сохраняются; consumer не получает полномочия install | K3 для версий и счётчиков peer/artifact |
| Unified report envelope | вложенная типизированная структура envelope + payload schema | внешняя валидность и payload-валидность проверяются отдельно | K3 для generation/version/count |
| 66-point capability profile | конечный каталог контролей с evidence/status relation | исторические источники и требования не равны runtime-функциям | K3 для номеров контролей и размеров диапазонов |
| Security / resilience | логическая система шлюзов, политика, статус доказательств | contract-only ≠ реализовано; default deny; unknown не является allow | счётчики событий, только типизированные статусы и версии |

## 3. Какие знания действительно переписываются в Kaskad

### 3.1. Новые формальные разделы
1. Многосортная предметная сигнатура OPlague.
2. Точная нормализация аппаратных ID.
3. Двудольный граф кандидатных соответствий.
4. Модель целостности UDRV-контейнера.
5. Реестр происхождения, HMAC-псевдонимы и конфликтующие данные.
6. Метрическая и статистическая модель профилей.
7. Частичная телеметрия с явным unknown.
8. Модель транзакций и поколений.
9. Модель LWW-регистра и условия сходимости.
10. DAG-планировщик и критический путь.
11. OCTA-сеть проектов и фасетные ограничения.
12. Каталоги 133 симуляционных операций и CSR-120.
13. Ординальная модель impact-профилей.
14. Математическая модель игрового эксперимента и условного возврата power plan.
15. Модель бюджетного баланса и контролируемой эволюции репозитория.

### 3.2. Что остаётся отдельным от K3
- байтовая строка и формат файла;
- строковый аппаратный идентификатор;
- криптографический дайджест и ключ HMAC;
- реальная метрика на вещественном пространстве;
- единица измерения и неопределённость;
- топология графа;
- доказательное происхождение;
- частичное значение unknown/null;
- набор тестов и результат CI.

Эти типы могут содержать числовые поля, но числовое поле не превращает весь объект в элемент \(\mathbb N_0\).

## 4. Проверка согласования с Теорией Вьюненко

| Каноническое положение K3 | Требование к прикладной модели OPlague |
|---|---|
| \(B=1000\) — фиксированное основание | все K3-числовые поля используют неизменное основание |
| группы имеют коэффициенты 0…999 | индекс/счётчик не должен превышать диапазон группы без переноса в старшие позиции |
| \(k\) — позиционный разделитель | не использовать \(k\) как оператор/значение единицы, хэш, namespace или произвольный разделитель |
| значение зависит от всех коэффициентов | нельзя отбрасывать нулевые группы или менять позицию счётчика при нормализации |
| каноническая форма отделена от PAD/RAW | импортные нормализации сохраняют исходную запись и след преобразования |
| числовое равенство ≠ структурное равенство | одинаковая сумма агрегатов не стирает порядок/структуру исходных отчётов |
| операционный след хранится отдельно | невозможно восстановить историю изменения только из конечного снимка |
| расширение не меняет базовую семантику без решения | OPlague-слой — прикладная надстройка, не новая аксиома K3 |

## 5. Открытые вопросы согласования

1. Закрепить одну согласованную OCTA-топологию в JSON, tests и project-contract.
2. Уточнить расхождение retry max_attempts=3 и общего текста max 10.
3. Отделить contract-only планы установки/восстановления от фактического read-only режима.
4. Формализовать полный класс источников и статусов свидетельств; связать их с VCL без автоматического повышения доверия.
5. Проверить по коду и тестам все пути, не рассмотренные в первичном аудите.
6. Зафиксировать единицы и правила квантования каждой метрики до применения K3.
7. Проверить, что подписи, HMAC, digest и псевдонимы не смешиваются с обычными числовыми идентификаторами.

## 6. Итог

OPlague становится в Kaskad не копией программного проекта, а математически описанной прикладной системой. Её ядро — типизированные наблюдения и свидетельства, ограниченные преобразования, граф кандидатных отношений, статистика, транзакции, локальное согласование, DAG и федерация. K3 остаётся фундаментальным позиционным слоем точных целых с основанием 1000, без потери размерностей, источников, типов и доказательной дисциплины.
